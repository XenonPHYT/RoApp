2. PRODUCT IDENTITY AND PURPOSE
======================================================================

Product name: RoApp RoApp is the actual name of the public Discord bot.

RoApp is a public Discord bot for Roblox communities. It helps
communities create, publish, receive, review, and process applications.

The companion website is called the “RoApp Dashboard”. It is linked to
the authenticated user’s Discord account. Do not describe the bot itself
as a “shared bot” in public-facing copy. It is a public Discord bot that
many communities can invite.

Core product statement: “Create, manage, and process community
applications through Discord and the RoApp Dashboard.”

The system has three main parts: A. RoApp Discord Bot — invited to
multiple Discord servers. B. RoApp Dashboard — website where authorized
Discord account holders manage their communities. C. RoApp backend — one
Cloudflare Worker and one D1 database for the initial release.

One public bot serves multiple Discord servers. Each server is an
independent tenant with isolated forms, applications, staff permissions,
settings, panels, and audit records.

6. DISCORD INTERFACE DESIGN
======================================================================

IMPORTANT: Build interfaces using real Discord capabilities. Do not
imitate a website dashboard inside Discord.

Discord supports: - Embeds with titles, descriptions, fields, colors,
thumbnails, images, and footers. - Link buttons and interactive
buttons. - String select menus and other supported select menu types. -
Modals with text inputs. - Ephemeral interaction responses. - Message
updates and follow-up responses.

Discord does NOT support arbitrary HTML, CSS, sidebars, custom card
layouts, or fully custom application windows inside a bot message.

Visual reference: The user supplied an example of a genuine Discord bot
embed with a long information embed and several native link buttons
underneath. RoApp should follow that practical Discord-native style:
clean embed, readable text, concise sections, and native buttons below
the embed. Do not recreate the fake multi-column interface mockup.

PUBLIC APPLICATION PANEL - A community owner/authorized manager
configures and publishes an application panel to a selected channel. -
The panel is a normal persistent bot message with a Discord embed and
native buttons/select menus. - It may list application categories,
descriptions, requirements, and whether each form is open or closed. -
Applicants click a button or select a form to begin. - Use modals for
short forms and/or a secure dashboard web form for longer or more
complex forms. - The panel message ID, channel ID, guild ID, panel type,
and configuration must be stored in D1. - RoApp should be able to update
an existing panel message instead of posting duplicates when a manager
edits its configuration. - Panel interactions must remain functional
after Worker redeployments because state is stored in D1, not only in
memory.

CENTRALIZED REVIEW EXPERIENCE - Avoid requiring multiple reviewer
channels for pending, approved, rejected, and other application
states. - A community may designate one channel for a permanent RoApp
management entry message, but reviewer work should primarily happen
through private ephemeral interactions. - An authorized staff member
invokes /review (or a review entry button if supported by the design). -
RoApp checks their current permissions. - RoApp responds ephemerally
with a simple embed and native dropdown/buttons. - Reviewers can select
Pending, Under Review, Awaiting Decision, Completed, My Assignments, or
Search. - The selected view is returned privately to that reviewer. - An
application can be opened privately with its details and permitted
actions. - Buttons may include View, Assign, Add Note, Approve, Reject,
Request Revision, or Move to Interview, depending on permissions. - The
same Discord message components may be visible to everyone who can see a
public message. Do not claim individual controls are hidden per user.
Use ephemeral responses for private reviewer interfaces. - Ephemeral
responses are interaction responses, not permanent messages. Do not rely
on them as persistent dashboards or long-lived stored messages.

PUBLIC VS PRIVATE DATA - Public application panel: no applicant private
answers. - Applicant confirmation: visible only to applicant when
practical. - Reviewer details: private/ephemeral and
permission-checked. - Internal notes: only authorized
reviewers/managers. - Final applicant notifications: only the relevant
applicant and authorized staff.

7. COMMANDS — INITIAL V1 PROPOSAL
======================================================================

Keep the number of slash commands manageable. Prefer a small number of
commands with subcommands and Discord components.

Applicant commands: - /apply — show available forms or start an
application. - /myapplications — show the caller’s own applications. -
/application view — view one of the caller’s own applications, subject
to ownership checks. - /application withdraw — withdraw an eligible
application belonging to the caller. - /help — show command guidance.

Reviewer commands: - /review — open the private reviewer interface. -
/queue — optional shortcut to the review queue if it proves useful;
avoid duplicate functionality if /review already covers it.

Community management commands: - /setup — begin initial server
configuration. - /dashboard — provide the RoApp Dashboard link. - /panel
publish — publish or update a public application panel. - /panel update
— update a panel. - /panel remove — remove a panel after confirmation. -
/forms list — list forms. - /forms create — create a draft form or
direct the manager to the dashboard form builder. - /forms publish —
publish a form. - /forms close — close a form. - /staff — show
staff/permission management guidance or dashboard link.

Do not implement every proposed command blindly. Keep commands that have
clear Discord-native value. More extensive form building, staff
configuration, analytics, and settings should be dashboard-first.

Platform administration: - Keep platform-owner operations separate from
community-owner operations. - Do not expose platform administration
commands to ordinary community administrators. - A private platform
admin dashboard may be preferable. Do not implement global commands
until a secure platform-owner identity model is defined.

COMMAND REGISTRATION - Use Discord application command registration
through scripts/register-commands.js. - Define commands in one
maintainable source of truth. - Do not duplicate command definitions in
multiple files. - Document development guild command registration and
global registration separately. - Do not deploy or register commands
against an invented Discord application ID.

8. DASHBOARD AUTHENTICATION AND AUTHORIZATION
======================================================================

Use Discord OAuth2 as the initial dashboard login.

Initial scopes: - identify - guilds only if server listing is required

The dashboard is linked to the authenticated Discord account, not
permanently to a single server. A user may manage multiple communities
from one account, but access is checked independently for every guild.

ACCESS POLICY: 1. The Discord server owner has full community dashboard
access by default. 2. The server owner may configure one or more Discord
roles that grant dashboard access. 3. Discord Administrator permission
does NOT automatically grant RoApp dashboard access. 4. Having
permission to manage the bot does NOT automatically grant dashboard
access. 5. Regular members have no dashboard management access unless
explicitly authorized. 6. Dashboard access roles and permissions are
configured per guild. 7. The platform owner is a separate
identity/authorization domain from each community owner.

For every protected dashboard request: - Validate the session. -
Identify the authenticated Discord user. - Resolve the selected guild
from server-side authorization context. - Verify the user is still the
guild owner or holds an allowed configured role. - Check the requested
granular permission. - Scope all D1 queries by guild_id. - Deny by
default if Discord authorization cannot be confirmed. - Do not trust
guild IDs, role IDs, or permissions asserted only by browser
JavaScript. - Avoid long-lived stale permission claims. Revalidate
current access as appropriate and provide session expiry/revocation.

Use secure session handling: HttpOnly, Secure, SameSite cookies where
compatible; CSRF protection for state-changing requests; OAuth state
validation; safe redirect URI validation; secure session identifiers;
and appropriate expiration/revocation.

10. D1 DATABASE REQUIREMENTS
======================================================================

Use ONE D1 database for the initial release.

Use ONE initial schema file: src/database/schema.sql

Do not create migrations/ for this brand-new database. The initial
schema is executed once against the newly created empty D1 database. If
schema evolution becomes necessary after launch, introduce migrations
later.

Initial logical table groups may include: - guilds - guild_settings -
dashboard_role_access - forms - form_versions - form_questions -
applications - application_answers - application_reviews -
application_notes - application_events - staff_members or staff
permission assignments, if needed - panels - dashboard_sessions (only if
server-side sessions are stored in D1) - notification_jobs (only if
persistent retry handling is implemented) - audit_logs

Do not create redundant tables. Explain the purpose of each table before
finalizing the schema.

Database rules: - Use primary keys and appropriate foreign keys. - Use
unique constraints for identifiers that must be unique. - Index common
lookups such as guild_id, applicant Discord ID, status, form ID, and
created_at. - Use composite constraints/indexes where tenant scoping
requires them. - Use prepared statements and D1 batch/transaction
patterns where appropriate. - Store timestamps in UTC in a consistent
format. - Avoid storing derived information unnecessarily. - Ensure that
all community-specific reads and writes are scoped to guild_id. - Avoid
cross-tenant data leakage even when a caller guesses another
application’s reference ID.

11. WORKER REQUEST ROUTING
======================================================================

Use one Worker entry point.

Expected high-level routes: - POST /api/discord/interactions — Discord
interaction endpoint. - GET /auth/discord — begin Discord OAuth2
authorization. - GET /auth/discord/callback — validate OAuth callback
and establish session. - POST /api/… — authenticated dashboard API
routes. - GET /… — static dashboard assets served through the configured
ASSETS binding.

Use clear routing. Do not add a routing framework unless the route count
becomes difficult to maintain.

The Worker should: 1. Handle Discord interaction requests. 2. Verify the
Discord request signature before parsing/acting on the interaction. 3.
Respond to Discord PING correctly. 4. Dispatch application commands,
component interactions, and modal submissions. 5. Route dashboard
authentication and API requests. 6. Serve static assets through
Cloudflare Workers assets. 7. Return safe errors without leaking secrets
or stack traces to users.

15. TESTING AND ACCEPTANCE CRITERIA
======================================================================

RoApp is not ready for release until the following are verified:

FOUNDATION - Worker starts locally. - Health route responds. - D1
binding works. - Initial schema applies cleanly to an empty D1

DISCORD - Invalid signatures are rejected. - Valid Discord PING receives
the correct response. - Slash commands are routed correctly. - Buttons,
selects, and modals are routed correctly. - Interaction responses meet
Discord timing requirements. - Persistent panel messages can be updated
using stored IDs.

MULTI-TENANCY - Guild A cannot view Guild B applications. - Guild A
cannot modify Guild B forms or settings. - Guessing another
application’s reference does not bypass guild scoping. -
Browser-supplied guild IDs are not trusted without server-side
authorization.

PERMISSIONS - Guild owner receives community management access. -
Configured dashboard roles receive only assigned access. - Discord
Administrator alone does not grant dashboard access. - Regular members
cannot access reviewer or dashboard controls. - Unauthorized component
interactions are denied. - Permission removal takes effect after
revalidation.

APPLICATIONS - Closed forms cannot accept new submissions. - Required
fields are enforced. - Application references are unique. - Form edits
do not alter old submission snapshots. - Applicants can only view or
withdraw their own eligible applications. - Internal notes remain
private.

REVIEW - Review interface is ephemeral. - Reviewer permissions are
checked on every action. - Decisions are recorded with actor and
timestamp. - Invalid status transitions are rejected. - Applicant
notifications do not expose internal notes.

DASHBOARD - OAuth state is validated. - Sessions are secure and
expire. - Guild selection does not grant access by itself. - API
endpoints enforce permissions server-side. - Dashboard works on mobile
and desktop.

PRODUCTION IMPLEMENTATION EXPECTATIONS

A. DISCORD BOT - Correctly verify Discord Ed25519 interaction
signatures. - Correctly handle PING. - Support the implemented slash
commands and register them using a repeatable script. - Support
Discord-native embeds, buttons, select menus, and modals. - Handle
public application panels and update stored panel messages using Discord
REST. - Handle private reviewer workflows with ephemeral interaction
responses. - Use valid Discord component structures and custom_id values
within Discord’s limits. - Handle expired, malformed, unauthorized, or
stale component interactions safely. - Respect Discord interaction
response deadlines and use deferred responses/follow-ups where
required. - Use bot token authentication only on the server. - Do not
require a persistent Gateway connection for the initial feature set.

B. APPLICATION ENGINE - Implement form definitions, published
versions/snapshots, question validation, submission, unique references,
applicant ownership, status history, and withdrawal rules. - Validate
required fields and limits on the server, not only in browser code or
Discord UI. - Ensure closed forms cannot accept submissions. - Ensure
old submissions remain tied to their original form version. - Prevent
duplicate or repeated decisions where inappropriate. - Keep internal
notes private.

C. REVIEW AND PERMISSIONS - Implement the centralized /review experience
using ephemeral Discord interactions. - Implement reviewer queue filters
and application detail views. - Implement role-based, per-guild
permissions. - The Discord guild owner has full community dashboard
access by default. - Only explicitly configured roles receive dashboard
access. - Discord Administrator permission alone must not grant
dashboard access. - Re-check permissions for every protected action. -
Do not rely on the visual presence or absence of buttons as a security
control. - Record decisions, assignments, notes, and privileged actions
in history/audit records.

D. DASHBOARD - Implement Discord OAuth2 login and callback with state
validation. - Implement secure server-side sessions and logout. -
Implement server-side authorization and guild isolation. - Implement
server selection based on the authenticated user’s actual guild
membership and the configured access policy. - Implement a responsive,
accessible dashboard using vanilla HTML, CSS, and JavaScript. -
Implement the agreed initial dashboard features: overview, forms,
applications, review details where appropriate, staff/permissions, panel
configuration, settings, and basic statistics. - Do not rely on
client-supplied guild IDs or permission claims. - Protect state-changing
operations against CSRF. - Validate redirect destinations and OAuth
callback parameters.

E. ROBLOX INTEGRATION - Implement public Roblox username resolution only
where supported by documented public endpoints. - Clearly distinguish
“username resolved” from “account ownership verified”. - Do not
implement fake verification or imply Roblox OAuth ownership verification
exists unless fully implemented and tested. - If an API is unavailable
or rate-limited, fail gracefully and explain the status.

F. NOTIFICATIONS - Implement applicant-facing status notifications
without exposing internal reviewer notes. - Handle Discord API errors
and rate limits correctly. - If reliable retry scheduling cannot be
implemented without adding infrastructure, document the limitation and
use a simple durable D1 retry approach only if it can be implemented
safely. Do not add Cloudflare Queues automatically.

G. DATABASE - Use one D1 database. - Include one complete initial schema
at src/database/schema.sql. - Include constraints, foreign keys,
indexes, and tenant-safe relationships. - Include a documented one-time
command to apply the schema to a new empty database. - Do not create a
migrations directory for the initial database. - Ensure queries always
enforce guild scope for tenant-owned data.

H. SECURITY - Perform a security review before packaging. - Check
authentication, authorization, tenant isolation, input validation, SQL
injection, CSRF, session handling, secret exposure, error leakage, and
